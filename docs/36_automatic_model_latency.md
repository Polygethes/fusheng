# 自动模型延迟与情感通道修复

日期：2026-09-07（America/Los_Angeles）。模型固定为 `gpt-5.6-sol`，推理等级 `medium`。

## 实验口径

使用真实 Codex CLI 模型供应商和人物独立持久会话，由脚本自动衔接阶段与回合；没有人工逐次提交，没有夹具替代行动回复。每组两个完整行动回合。每次调用最多等待 600 秒；两调用组最多 6 次请求，三调用组最多 8 次请求，包括有限的协议修复。

两组从同一份世界检查点开始。三个已录制的日计划是固定前置条件，不算这次模型生成；人物在堂前，初始执行顺序从谢真石开始。后续模型选择不同会使第二回合上下文不同，因此这是一组小样本对照，不是逐阶段内容完全相同的性能证明。

计时从 CLI 启动到最终 JSON 返回，包含 CLI、网络、服务端排队与生成。第一条 CLI 事件和完整 `agent_message` 的时间只作诊断，不能冒充首 token 延迟。CLI 用量事件按原样保存，可能包含会话累计计数，不相加作为本次 token 消耗。

## 已复现的缺陷与修复 

原始谢真石回复在两调用路径中稳定触发 `CHARACTER_AGENT_AFFECTIVE_CHANNEL_NOT_LIVE`：它选择了 `responseLatency`，但实际调节后的通道只有 `attentionLock`、`gaze`、`pace`、`orientation`、`movementInterruption`、`voiceOnset`。

因果原因是第二次调用同时要求人物选择调节方式、写出调节后的表达。调节方式尚未返回，本地数学尚不能计算结果，此时四个候选的 `affectiveResidue` 全是空列表。模型被要求引用尚未提供的真实结果。

新增可选 `three-call` 路径：

1. 人物主观评估并生成候选；本地心理数学评价候选。
2. 同一人物选择动作和调节方式；本地计算实际调节结果。
3. 同一人物收到这个已选动作的表达现场，生成公开表达并提交；世界结算。

同时收紧独立表达阶段的输出 Schema：只列出实际提供的情感通道、达到实质影响阈值的情绪；没有实质残余时只允许 `no_live_influence`。不再在 Schema 中提供校验器必然拒绝的引用。矛盾的本地约束会在调用前报错。原有世界与心理校验保留，系统不改写人物表达，不替人物选择动作。

复用原录制的评估、已选动作与已修正表达，三调用路径无需修复即可结算。该项是确定性回放，不计入真实模型实验。

## 实测结果

**两组均完成，但没有测出提速。** 三调用组减少了提示体积、消除了这两个样本的协议修复，总时长却增加了 **14.7%**，因此保留浏览器原来的两调用默认。新增路径作为因果顺序更完整的可选方案；不能把它宣传成已经加速。

| 两个完整行动回合 | 两调用基线 | 三调用修复方案 |
|---|---:|---:|
| 总墙钟 | 541.98 秒（9 分 2 秒） | 621.87 秒（10 分 22 秒） |
| CLI 模型调用累计 | 541.75 秒 | 621.67 秒 |
| 调用以外处理累计 | 223.81 ms | 204.92 ms |
| 实际调用次数 | 5 | 6 |
| 协议修复 | 1 | 0 |
| 所发送提示合计（UTF-8 字节） | 1,086,274 | 751,433 |
| 世界结算 | 2 次成功 | 2 次成功 |

提示体积减少 **30.8%**，这不是 token 数下降的测量。三调用正常路径多一次调用；相对于没有修复的基线回合，这个成本不可忽略。两个独立样本也不足以证明普遍的故障率或速度变化。

基线的洛照真实返回再次触发 `CHARACTER_AGENT_AFFECTIVE_CHANNEL_NOT_LIVE`：模型写了 `gaze`，实际表达现场只提供 `attentionLock`，第三次调用改为实际通道后通过。三调用组的两次表达都在拿到真实调节结果后一次通过。

第一阶段占两组回合总时长的 **71.3% / 68.5%**；单次 176–217 秒。在完全自动衔接、无人工提交的条件下，它仍然很慢。调用外开销仅约 0.04% / 0.03%，继续优化这里不能明显改变体验。CLI 启动事件约在 0.19–3.08 秒出现，但这不是首 token；记录中也有非终止的 CLI `error` 项，未归档其正文，不能将全部调用时间进一步归因为纯模型推理。

这四个行动均没有对白，模型自行选择了移动或观察。下表原样保留其公开表达，不补写台词；世界结算另外列出。

| 路径 | 人物 | 模型原文 | 世界结果 |
|---|---|---|---|
| 两调用 | 谢真石 | 公开对白与动作文字均为空；结构化提交为 `move` | 从堂前移动到后院，成功 |
| 两调用 | 洛照 | 她转眼望向后院，观察那人的去向。 | 建立对谢真石的视觉观察，成功 |

这些输出表现出“谢真石离开堂前，洛照继续观察”的连续行为；四个短行动不能证明长篇人物表现质量。世界成功结算也不等于人类已经认可文学质量。

## 下一步提速方案

优先处理第一阶段模型工作量。实测其首次提示为 190 KB；紧凑输入中 `worldProjection` 约 58 KB、`privateContext` 约 37 KB、`situationalGrounding` 约 14 KB。当前第一阶段真实返回中，候选约 9 KB，评估约 6–7 KB。它们比本地构造这些对象的成本更值得优化。

1. 为人物输入做可逆去重，固定资料只保留一份定义，以引用连接重复部分；继续按人物可知范围投递变化。不能通过删掉本人已注意的事实、心理来源或长期欲望来缩短输入。
2. 试验紧凑的传输字段与引用编码，由确定性适配层还原为现有协议；保持原有候选数量、人物选择权和验收规则。这能直接针对反复生成的大段结构文字，而不是只缩小 HTTP 包。
3. 继续用同模型、同初始状态的自动测试验收，分别计入首次资料加载与后续回合，记录输入、输出、调用总时长、修复率和真实公开行为。不能把成本挪到预热里后宣称提速。

以上是下一轮实验方案，尚未实现或证明收益。本次不降低 medium 推理等级、不更换模型，也不以丢弃心理因果约束换取表面吞吐。

## 当前中继的版本差异

本次只读检查发现，8791 端口运行的是外层 `.gtown-run-artifacts/sim-model-relay.mjs` 的旧复制文件，仍有阻塞式 `/respond`，没有 `/metrics` 或 `/pending`。仓库中的新中继已经修复，旧进程不会自动加载仓库改动。检查时旧世界停在 5 个已结算回合、等待周珉回复；本实验使用独立世界，没有停掉或改写这个进程。

其日志的 `genMs` 从 pending 到外部提交计时，仍包括调用方编排；部分回复文件在服务启动前就已存在。因此日计划的 4.86 秒不能作为本次新生成的纯模型耗时，也不能据此推出每阶段 5–15 秒。

后续手工中继应从项目目录使用 `npm run relay:start`，按 [中继诊断](35_relay_latency_diagnosis.md) 的 `stageId` 协议提交。已有进程的内存状态须另行处理，不能直接杀进程来“升级”。
