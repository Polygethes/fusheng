# 人物小镇 Character Town 产品草案

## 0. 项目定位

人物小镇是一个由模型驱动的深层人物叙事沙盘。

用户不是普通读者，也不是只输入一句话等待故事输出的人。用户是小镇操盘手。

用户先创建一组复杂人物，再创建一个能逼人物行动的场所。随后用户选择哪些人物进入某个空间，点击“播放”，系统分别驱动每个人物的独立行动线，再由场景模型合成一段发生在小镇中的故事。用户点击“赞同”后，该事件进入正史，影响后续人物记忆、关系、谣言、证据和不可逆后果。

一句话：

> 人物小镇不是自动写小说工具，而是复杂人物关系的动态生成系统。

---

## 1. 核心价值

普通 AI 写作工具通常从“情节”出发：

```text
输入设定 → 输出大纲 → 输出章节
```

人物小镇从“人物行动系统”出发：

```text
创建复杂人物 → 放入压力场 → 独立驱动行动线 → 互相误读和污染 → 用户确认正史 → 故事持续生长
```

它解决的问题：

- 普通角色太平。
- 故事太像情节安排。
- 人物不主动，只服务主线。
- 道德修复过快，缺少人性多义。
- 关系变化不深，只有喜欢、讨厌、冲突。
- 作者想探索人物，但模型总是给安全、正确、体面的版本。
- 作者需要一个可操盘、可分支、可沉淀正史的叙事环境。

---

## 2. 产品原则

1. 人物优先于情节。
2. 行动优先于解释。
3. 关系优先于事件。
4. 多义性优先于正确性。
5. 不可逆后果优先于安全收束。
6. 每个主要人物都有独立行动线。
7. 用户决定什么成为正史。
8. 模型负责推进可能性，不负责替用户关闭可能性。
9. 小镇是压力机器，不是背景板。
10. 角色不是棋子，而是会反抗操盘手预期的行动体。

---

## 3. 核心用户

```yaml
核心用户:
  小说作者:
    需求: 生成复杂角色和长期故事张力。

  编剧:
    需求: 生成关系驱动的场景和角色弧线。

  游戏叙事设计师:
    需求: 建立角色代理、事件系统和动态剧情。

  互动叙事创作者:
    需求: 让用户选择人物、事件、分支和正史。

  导演/表演创作者:
    需求: 用行动、潜台词和规定情境深化角色。

  角色创作者:
    需求: 从普通人设生成能行动的深层人物。
```

---

## 4. MVP 范围

第一版只做四个核心页面：

```yaml
MVP页面:
  1_角色工坊:
    功能: 生成和编辑深层角色卡。

  2_小镇工坊:
    功能: 生成和编辑小镇场域。

  3_操盘台:
    功能: 选择人物、地点、播放粒度、注入事件、点击播放、点击赞同。

  4_档案室:
    功能: 查看正史时间线、草稿分支、角色记忆、关系变化、秘密、证据、谣言。
```

第一版不需要完整地图编辑器、不需要复杂动画、不需要多人协作、不需要实时 3D。重点是叙事状态和模型驱动闭环。

## 5. 用户核心流程

```yaml
用户流程:
  Step_1_创建项目:
    用户输入项目名、题材、黑暗度、现实/幻想程度。

  Step_2_创建小镇:
    用户输入一句场所概念。
    系统生成小镇档案、空间卡、权力结构、秘密、谣言和事件库。

  Step_3_创建人物:
    用户输入人物概念。
    系统生成深层角色卡。
    用户编辑、锁定或重生成部分字段。

  Step_4_选择场景:
    用户在操盘台选择地点、时间、参与人物、播放粒度。

  Step_5_点击播放:
    系统分别驱动每个人物的独立行动线。
    导演模型合成场景。

  Step_6_查看剖面:
    系统展示表面事件、每个人的显性行动、隐藏行动、阴影行动、潜台词和关系变化。

  Step_7_用户确认:
    用户点击赞同、部分赞同、重掷、变体或注入事件。

  Step_8_进入正史:
    被赞同的内容写入正史，更新人物记忆、关系、谣言、证据、秘密和不可逆痕迹。

  Step_9_继续播放:
    后续每一次播放都读取正史状态，不从零开始。
```

## 6. 核心页面设计

### 6.1 角色工坊

目标：生成深层角色卡。

核心组件：

```yaml
角色工坊组件:
  角色输入框:
    示例: 一个以师德自持但害怕自己普通欲望的大学教师。

  生成按钮:
    输出完整角色卡。

  角色卡编辑器:
    可编辑:
      - 自我神话
      - 显性行动线
      - 欲望行动线
      - 防御行动线
      - 阴影行动线
      - 触发器
      - 关系规则
      - 不可逆边界

  深化按钮:
    对角色某一部分进行更深挖掘。

  锁定按钮:
    锁定用户满意的字段，重生成时不改变。

  质量检查:
    检测角色是否扁平、单义、太干净或缺少反行动。
```

角色工坊输出必须包含：

```yaml
角色卡:
  基础身份:
  规定情境:
  自我神话:
  四条行动线:
  欲望滞后:
  羞耻机制:
  防御语言:
  阴影行动:
  高尚行动:
  卑劣行动:
  内心法庭:
  行动动词库:
  触发器:
  关系规则:
  不可逆边界:
```

### 6.3 操盘台

目标：驱动故事发生。

页面布局：

```text
┌──────────────────────────────────────────────────────────────┐
│ 人物小镇 / 操盘台                                             │
├────────────────┬─────────────────────────────┬───────────────┤
│ 人物列表        │ 当前场景                      │ 操盘面板       │
│                │                             │               │
│ ☑ 角色A         │ 地点：第二教学楼走廊           │ [播放]         │
│ ☑ 角色B         │ 时间：周三傍晚                 │ [暂停]         │
│ ☐ 角色C         │                             │ [赞同]         │
│ ☐ 角色D         │ 生成的场景文本……               │ [部分赞同]     │
│                │                             │ [重掷]         │
│                │                             │ [注入事件]     │
│                │                             │ [深挖人物]     │
│                │                             │ [查看潜台词]   │
├────────────────┴─────────────────────────────┴───────────────┤
│ 正史时间线 / 草稿分支 / 关系变化 / 证据记录 / 谣言             │
└──────────────────────────────────────────────────────────────┘
```

操盘台核心控件：

```yaml
播放:
  推进下一拍、下一场、下一天或下一周。

赞同:
  把本次生成内容写入正史。

部分赞同:
  用户选择保留哪些动作、台词、关系变化和证据。

重掷:
  保留当前状态，重新生成另一种可能。

注入事件:
  插入用户指定或系统推荐的意外事件。

深挖人物:
  对当前人物行动做多重动机拆解。

查看潜台词:
  显示台词和行动的隐藏任务。

调整强度:
  可调节:
    - 黑暗度
    - 高尚度
    - 关系互染度
    - 不可逆程度
    - 现实主义程度
```

### 6.4 档案室

目标：保存和查看正史。

```yaml
档案室:
  正史时间线:
    所有被赞同的事件。

  草稿分支:
    未确认或废弃的可能性。

  人物记忆:
    每个角色知道什么、误解什么、隐瞒什么。

  关系档案:
    角色之间的爱慕、厌恶、依赖、权力、欺骗、羞耻、报复。

  证据档案:
    邮件、录音、批注、监控、照片、旧信、修订记录。

  谣言档案:
    当前小镇流传的版本、传播者、受益者、受损者。

  不可逆痕迹:
    角色无法收回的动作、话语、证据和关系变化。
```

## 7. 播放机制

“播放”是产品核心。它不是播放视频，而是推进叙事时间单位。

```yaml
播放按钮执行流程:
  1_读取状态:
    读取小镇状态、角色状态、关系状态、正史、秘密、证据和谣言。

  2_独立角色生成:
    每个被选中角色的代理独立生成下一步行动意图。
    角色代理之间暂时互相不可见。

  3_冲突分析:
    导演模型比较角色意图，找出冲突、误读、共谋、保护、背叛、诱导。

  4_场景合成:
    导演模型生成场景文本或事件摘要。

  5_剖面输出:
    系统显示每个人表面做了什么、真正想做什么、隐藏了什么。

  6_状态建议:
    系统提出关系、记忆、证据、谣言和不可逆痕迹的更新建议。

  7_等待用户确认:
    用户赞同后才写入正史。
```

播放粒度：

```yaml
播放粒度:
  一拍:
    一个动作、眼神、台词、犹豫或选择。

  一场:
    一个完整场景。

  一天:
    多个人物分别发生行动，再汇总成小镇状态。

  一周:
    谣言扩散、制度推进、关系发酵、秘密变形。
```

---

## 8. 赞同机制

“赞同”不是点赞，而是确认正史。

```yaml
赞同按钮:
  功能:
    - 确认事件发生。
    - 写入正史时间线。
    - 更新人物记忆。
    - 更新人物关系。
    - 更新小镇谣言。
    - 更新证据系统。
    - 更新不可逆痕迹。
```

赞同类型：

```yaml
赞同类型:
  完全赞同:
    本次生成全部成为正史。

  部分赞同:
    用户选择保留哪些动作、台词、关系变化和证据。

  赞同但变体:
    用户保留方向，但修改具体行为。

  不赞同:
    废弃本次生成，保留在草稿分支或删除。

  锁定:
    用户把某个事实设为不可更改。
```

## 9. 角色代理

每个角色都是独立线路。

```yaml
角色代理输入:
  角色卡:
  当前记忆:
  当前关系:
  当前欲望强度:
  当前羞耻强度:
  当前愤怒强度:
  当前爱慕强度:
  当前厌恶强度:
  当前外部压力:
  当前秘密风险:
  当前所在空间:
  最近正史事件:

角色代理输出:
  显性行动:
  隐藏行动:
  防御行动:
  阴影行动:
  伪装理由:
  想从对方那里得到什么:
  不愿承认的快感:
  可能造成的伤害:
  可能留下的证据:
  下一步欲望变化:
```

角色代理不负责让整体故事“合理收束”。它只负责忠实于该人物的内在行动逻辑。

## 10. 导演模型

导演模型负责把多个人物行动合成为场景。

```yaml
导演模型输入:
  多个角色代理输出:
  当前地点:
  当前小镇状态:
  当前正史:
  用户本轮指令:
  播放粒度:

导演模型输出:
  场景文本:
  表面事件:
  潜台词动作:
  关系变化:
  证据变化:
  谣言变化:
  不可逆痕迹:
  可供用户选择的分支:
```

导演模型不得强行道德修复，不得让人物太快说出正确答案。

---

## 11. 深度检测模型

系统必须有一个“反安全叙事检测器”。

```yaml
反安全叙事检测:
  是否有人物太干净:
  是否有人物只是受害者:
  是否有人物只是加害者:
  是否把欲望直接写成问题并解决:
  是否把道德写成天然正确:
  是否用制度流程替代人物关系:
  是否让忏悔自动净化人物:
  是否让结尾恢复秩序:
  是否让复杂关系被一句正确话语解决:
  是否缺少不可逆行动:
  是否某个角色没有反行动:
```

修复规则：

```yaml
修复规则:
  人物太干净:
    增加阴影行动。

  人物只是受害者:
    增加反行动、误读、爱、恨、保护、报复或利用。

  结局太安全:
    增加不可逆后果。

  行动太单义:
    拆成高尚、欲望、羞耻、权力、自欺五层。

  关系太单向:
    强制生成三轮互染。

  场所太背景:
    增加谣言、证据、潜规则和逃离成本。
```

```http
POST /api/towns/generate
```

```http

```

```json
{
  "project_id": "project_001",

```

## 14. 模型提示链

播放时使用多阶段提示链。

```yaml
Prompt_1_角色代理:
  目标: 每个角色独立生成下一步行动。
  输入: 角色卡 + 个人状态 + 关系状态 + 小镇压力。
  输出: 显性行动、隐藏行动、防御行动、阴影行动。

Prompt_2_行动碰撞:
  目标: 检测多个人物行动之间的冲突、误读、共谋。
  输入: 所有角色代理输出。
  输出: 场景核心张力。

Prompt_3_导演合成:
  目标: 生成场景文本。
  输入: 场景核心张力 + 地点 + 正史。
  输出: 场景草稿。

Prompt_4_状态更新:
  目标: 从场景中提取记忆、关系、证据、谣言、不可逆痕迹。
  输出: 状态更新建议。

Prompt_5_深度检测:
  目标: 检查是否扁平、安全、单义。
  输出: 问题与修复建议。
```

## 17. 核心评估指标

```yaml
角色深度指标:
  每个主要人物是否有四条行动线:
  每个关键行动是否有多重动机:
  高尚行动是否混入阴影:
  恶意行动是否混入爱、恐惧或求救:
  人物是否能主动改变其他人物:

关系深度指标:
  是否至少三轮互染:
  是否存在误读:
  是否存在双方都不愿承认的收益:
  是否关系变化不可逆:

场所强度指标:
  是否有权力结构:
  是否有潜规则:
  是否有谣言系统:
  是否有证据系统:
  是否有逃离成本:

用户体验指标:
  用户是否能快速生成一个可运行小镇:
  播放结果是否出乎意料但合理:
  赞同后状态是否持续影响后续:
```

## 18. 产品风险

```yaml
风险_1_模型输出安全收束:
  表现: 人物太快道歉、修复、保护、恢复秩序。
  应对: 深度检测模型强制重写。

风险_2_人物过度黑化:
  表现: 角色只有邪恶，没有爱、恐惧、求救或高尚。
  应对: 恶意行动复杂化检查。

风险_3_角色白纸化:
  表现: 某个角色只承受主角行动。
  应对: 角色四线检查和反行动生成。

风险_4_状态遗忘:
  表现: 后续剧情不记得之前正史。
  应对: 正史摘要 + 角色记忆 + 关系状态持久化。

风险_5_用户控制感弱:
  表现: 用户只是看模型生成。
  应对: 赞同、部分赞同、锁定、注入事件、重掷、编辑状态。

风险_6_复杂度过高:
  表现: 用户看不懂系统。
  应对: MVP 先做角色工坊、小镇工坊、操盘台、档案室四页。
```

## 20. 第一版成功标准

第一版成功，不是因为它能生成漂亮文本，而是因为它能做到：

```yaml
成功标准:
  1: 用户能在 10 分钟内创建一个小镇和 3 个复杂人物。
  2: 每个角色都能以独立行动线参与场景。
  3: 播放一次后，至少产生一个关系变化。
  4: 赞同后，后续播放能继承该变化。
  5: 系统能指出某个角色是否太白纸或太单义。
  6: 用户能注入事件并观察人物反应。
  7: 至少一次播放结果让用户觉得“这不是我直接安排的，但人物会这样做”。
```
