# 场景进展、物品反馈与恢复修复

日期：2026-09-15。基线：`d4fe0d4`。针对新场景 100 回合中“对白说完成、物品仍未变化”、闲聊掩盖停滞、回话目标错误和恢复丢失证据的问题。

## 已修复的断点

- **明确操作入口。** 工作、服务、验收的可用操作直接携带 `attemptPrimitive` 和 `actionBinding`，保留操作名称、条件与耗时。工作操作不能绑定成通用接触；只给一个物品编号也不能冒充具体工作操作。输出枚举限制可见操作，提交预检和候选验收检查操作与动作的配对，不从自然语言猜测或替换人物的选择。跨字段配对不使用不完整的对象 Schema 分支，避免严格输出模式的兼容性问题。
- **分清触碰、开始与完成。** 普通接触的本人回执明确说“仅触碰，没有启动工作，也没有改变物料、容器内容或交付状态”。启动工作时明确“尚未完成”；收尾时才给出完成和实际资源变化。放下、递交与逐件验收也分别记录。人物仍可说错话或误判，但对白和主观意图不成为物理完成依据。
- **补上近处的物理状态。** 人物可看到身边水缸和水桶的装载比例、柴束数量、器皿是否为空等限定字段。隔区资源、隐藏物品、包内物品与任意内部状态不会因此公开。反馈里的变化量来自本次实际结算，不来自人物预估。时间与等待经历也保留到最终表达阶段。
- **闲聊不再清除被动循环。** 重复看、听、休息或仅触碰物品的记录独立保留。实际物理变化、过程就绪、已发生的验收和身体恢复可以解除停滞；背景对白不算这些事情的进展。直接对停滞人物说话仍给本人一个回应机会，但不会清空先前的被动循环与复核历史。程序不强制人物去做工。
- **群聊回话提前校验。** 对话锚点明确给出本次 `reply` 能回应的上一位说话人。对同一群聊里的其他人说话，可以由人物另选 `continue` 或新谈话；不能因为对方也在线程里，就把它当成对最新来话的回复。错误在可修复的模型提交阶段发现。
- **恢复保留原证据范围。** 人物回合开始时冻结由宿主登记的可用证据，随未完成回合保存。私人状态更新移除即时自我证据后，恢复仍按原范围结算，不再清空注意记录才能继续。这个范围不能由模型输出补写。

这里没有用关键词拦截人物对白，也没有把“想劈柴”自动改成“拿斧头”。模型仍可能选择无效接触或坚持错误理解；修复确保它收到清楚的实际反馈，且相同空转不会无限耗尽回合。

## 下一轮中继读取方式

新增正式读取入口：

```bash
npm run relay:read
```

默认连接 `http://127.0.0.1:8791`；其他端口通过 `RELAY_BASE_URL` 设置。服务需重启到本次代码。

读取结果包含当前 `stageId`、完整 `systemPrompt`、无损共享格式的 `userPrompt`、冻结 `schema` 和 `submissionContract`。HTTP 对应入口是 `GET /pending?format=model`；原始 `GET /pending` 仍可用。两者都只是读取，不推进阶段。

本轮自建 `relay-peer.mjs` 摘要省略了期限、等待经历和操作详情。它作为历史测试证据保持原样；新测试使用正式入口，不再只把那个摘要作为模型上下文。不得把 `schema`、工作前提或客观回执中的字段裁掉后，宣称模型已经读过完整输入。

提交使用 `{stageId, output}`。`POST /validate` 是不消耗阶段的只读预检；`POST /respond` 的 422 已消耗一次有界提交，必须读取下一待回应阶段，不能用旧 `stageId` 改写已收件内容。202 只确认收件，不能视为动作成功。

已完成的旧存档保留人物记忆和原有错误认识。比较行为改善宜从相同初始场景新开测试；旧的未完成阶段仍受其冻结输入与输出约束保护，不应直接修改已接受选择、证据清单或停止标记来强行通过。
