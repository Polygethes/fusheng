# 中继提交挂起与阶段耗时诊断

日期：2026-09-07。检查基线为 `2757d88`，实际中继为 `sim-runs/2026-09-07-pi-model-20turns/sim-model-relay.mjs`。

后续同日检查发现，用户保留的 8791 进程运行的是外层目录中的旧复制文件，并未加载本文修复。本文的性能数字属于明确注明的本地控制测试；后续真实 Sol medium 自动运行、情感通道根因及进程版本核对见 [自动模型延迟报告](36_automatic_model_latency.md)。

## 结论

已确认并修复一个能造成每次提交长时间挂起的中继缺陷。旧 `/respond` 在交出本次回复之后，继续 `await schedulePump()`；后者排在当前整条驱动链之后，而当前驱动链又在等待下一阶段的外部回复。顺序调用的客户端因而必须先等超时，才能取得并回复下一阶段。

这个缺陷在只有一个日计划、无候选上下文展开的场景里就能稳定重现。两次最小测试中，提交分别在 1504.9 / 1505.4 ms 达到测试超时，但并发状态查询分别只需 3.7 / 2.7 ms，且下一阶段已经就绪。正式回归在修复前同样于 2003.8 ms 超时，修复后完成。

因此，用户记录中的 240 秒请求超时不能直接归为 Schema 构造或深拷贝耗时。旧中继还将每次阶段的 `elapsedMs` 固定填写为 `1`，该字段不能作为真实计时证据。

用户提供的总时长约 5 小时 48 分包含搭建、调试、外部回复、等待与重试；当前归档保留了实录和日计划，没有完整的逐阶段原始输入输出和时间轨迹，无法据此准确拆分历史占比。本次不把文件时间戳反推成 CPU 耗时。

## 本次修改

- `/respond` 立即返回收件确认，由当前唯一驱动继续校验和结算；不再追加或等待新的驱动任务。`/extend` 同样不等待模型回复。
- 每次调用分配唯一 `stageId`，包括同一人物、同一回合、同一阶段的协议修复。完整读取请求后再核对编号，防止并发请求误交给后来的人物。
- 同编号、同内容重发只确认一次；旧编号、异内容重发、另一运行的编号均不会消费当前等待项。
- 记录阶段输入准备、Schema 构造、输入大小、外部回复等待和回合本地处理耗时。待回复阶段的等待时长实时增长；尚未返回的耗时保留为 `null`。
- 增加简要进度与独立待回复接口，避免进度轮询反复取回完整人物上下文；修正归档位置下的导入路径。

角色仍填写原有主观评估、候选、选择和表达。生产模型提示、人物心理数学、候选数量规则、世界结算和校验器没有为这次修复改动。

## 20 回合控制测试

复现入口为 `npm run benchmark:relay`，完整测量见 [原始计时 JSON](35_relay_latency_benchmark_2026-09-07.json)。本机 Node.js 25.6.0，macOS arm64；计时期间未同时运行完整测试套件。

这是同一起始设置、三个角色的**本地合成控制样本**，不是对原先 20 回合真实模型输出的回放，也不是模型推理测速。样本有 20 个结算回合：16 个动作、3 个日计划、1 个反思，总计 36 次阶段回复。原历史实录则是 17 个动作和 3 个日计划，二者不混同。

先用既有确定性夹具捕获四阶段合法返回，再把同样内容通过两次调用路径结算。七候选样本使用七份分别编号、形状相同的候选测试上下文构造压力，不将其视为七种真实人物决策。核对仅排除四调用/两调用的供应商阶段名称差异；公开动作、投递、世界结果及所核对的人物私有选择均相同。

| 指标 | 每次 1 个候选 | 每次 7 个候选 |
|---|---:|---:|
| 20 回合本地运行时总耗时 | 567.1 ms | 627.2 ms |
| Schema 构造总耗时 | 7.55 ms | 6.74 ms |
| Schema 构造单次最大值 | 0.52 ms | 0.32 ms |
| 阶段输入准备单次最大值 | 12.68 ms | 11.42 ms |
| structuredClone 调用数 | 39,453 | 44,727 |
| structuredClone 累计耗时 | 468.8 ms | 517.5 ms |
| 阶段输入加 Schema 最大紧凑 JSON 大小 | 232,510 字节 | 401,453 字节 |

深拷贝确实占较多本地处理时间，但这组控制样本中其总量约半秒；没有复现每阶段数分钟的计算。测量包含计时探针，单次 Schema 的微小差异不用于声称七候选反而更快。它也不能排除未归档的更大输入在其他机器上的性能问题。

随后用七候选的同一份返回通过**实际 HTTP 中继**完成全部 20 回合，每次回复人为等待 25 ms，以检验计算与外部等待是否被分开：

| 指标 | 修复后实测 |
|---|---:|
| 36 次提交确认 p50 / p95 / 最大 | 1.03 / 1.49 / 2.81 ms |
| 20 回合本地处理累计 | 802.7 ms |
| 外部回复与控制端等待累计 | 1,109.0 ms |
| Schema 构造累计 | 8.70 ms |
| 含服务启动的总时间 | 2,034.3 ms |
| 行为及世界结算核对 | 与控制样本一致 |

这约 2 秒的结果来自本地测试回复，不能宣传成真实模型 20 回合从 5 小时 48 分降到 2 秒。本次已消除可复现的提交等待错误；模型推理、外部编排和真实内容修复所需时间，要在下一次真实运行中用新计时记录判断。

## 使用与客户端迁移

项目根目录运行 `npm run relay:start`，默认仅监听 `127.0.0.1:8791`。可通过 `RELAY_PORT` 和 `RELAY_TURN_LIMIT` 配置端口与结算回合上限。启动服务本身不会调用模型；由外部模型调用方处理待回复阶段。

1. `GET /status?compact=1` 查询进度、错误、当前阶段编号和等待时长；`complete` 是结算计数达到上限。
2. `GET /pending` 获取 `{ pending }`，其中有 `stageId`、人物、回合、阶段、完整输入和输出 Schema。
3. `POST /respond` 发送外层 `{ "stageId": "原样复制本次编号", "output": {} }`。这里的空对象仅示意，实际必须放入对应阶段的完整模型返回。
4. `202` 仅表示收件成功。继续获取进度与下一阶段；内容校验结果见 `/metrics` 的阶段记录，最终世界结果见 `/status` 的结算列表。不要等待这笔提交返回下一阶段。
5. 响应丢失时原样重发同一编号和内容，重复收件返回 `200`。`409` 表示过期编号或同编号内容冲突，应先重新读取当前阶段，不能把旧回复套到新编号。

`GET /metrics` 返回的 `responseWaitMs` 包含外部模型、操作者及调用方编排等待；它不是纯推理耗时。每回合 `localElapsedMs` 是墙钟总时长扣除上述等待，包含运行时和中继工作，也不是单独 CPU 时间。各字段有包含关系，例如 Schema 时间已经包含在本地处理时间中，不能再次相加。

计时数据保留在中继进程内，应在停止前保存 `/metrics` 与 `/status`。本次不新增服务端存档或外部模型会话持久化能力。原来只提交裸模型 JSON 的客户端必须按上述外层格式更新，否则明确返回 `400`。
