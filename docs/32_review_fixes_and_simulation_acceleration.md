### 运行和兼容边界

- 需要 **Node.js 24+**；本机验证版本为 25.6.0。升级后重启服务，避免新旧锁实现同时操作一个持久目录。
- 默认服务端数据目录为 `~/.local/state/character-town-v12/world-runtime-sessions`，可由 `GTOWN_RUNTIME_SESSION_DIR` 覆盖；`XDG_STATE_HOME` 也会影响默认根目录。备份要同时保留浏览器存档与该目录，包括新增的 `snapshots/`。
- 旧版只有浏览器引用的存档，仅当精确服务端代际仍在时可以升级恢复；已被清理的版本会明确报错，不能补造历史世界。
- 主 UI 的本地模拟和 JSON API 模型上下文支持快照。Codex CLI / subagent 的外部可变会话尚无历史分支能力，快照接口会明确拒绝这两类上下文，避免复制外部会话 ID 后混入另一时间线的模型历史。
- 命名快照不会随滚动历史删除；删除浏览器存档暂不自动回收服务端快照。后续可增加按引用清理，不能直接套用代际保留策略。
- 验证使用本地确定性夹具和合成 provider，没有发出真实模型请求；没有进行真实模型的质量或延迟评测。

## 加速基线

复现入口：`npm run benchmark:simulation`。原始数字见 [本地基线 JSON](./32_simulation_latency_baseline_2026-09-06.json)，脚本为 [benchmarkV27LocalLatency.mjs](../scripts/benchmarkV27LocalLatency.mjs)。

测量配置与主 UI 本地 adapter 一致：谢真石、洛照两个活动人物，堂前起始位置，启用日计划。连续 3 轮、每轮最多 40 个命令，总计 120 个人物回合；热回合统计排除 3 次启动，包含行动、计划或反思等运行时安排的回合。时间覆盖 adapter 和真实持久化，**不包括 HTTP、浏览器渲染、2.1 秒展示间隔或真实模型推理**。硬件环境为本机 macOS arm64、Node.js 25.6.0。

| 指标 | 中位数 | p95 / 范围 |
|---|---:|---:|
| 热回合服务端耗时（117 个） | 163.78 ms | p95 271.75 ms |
| 同一回合内存储调用累计耗时 | 118.95 ms | p95 176.24 ms |
| 启动命令（3 个，仅描述样本） | 107.50 ms | 103.80–145.52 ms |
| 单个完整代际文件 | 1.52 MB | 0.76–2.76 MB，十进制 MB |
| UI 正常模式每回合完成后的等待 | 2,100 ms | `src/ui/npcActivityLoop.js` 的 `npcActivityIntervalMs` |

另用两人物、无先前模型 transcript 的受控首动作，采集生产 `two-call` 提示构造结果：第一次 user 文本 **148,907 字节**，第二次 **206,263 字节**；对应 schema 分别 **34,742 / 10,828 字节**。这是 UTF-8 文本大小，**不是 token 数、真实请求总大小或真实模型延迟**。真实模型页启用了日计划，历史上下文和实际调用大小会变化。

源码同时确认：

1. `npcActivityLoop.js` 在上一回合完成后才追加展示等待，所以连续耗时是“回合时间 + 2.1 秒”。
2. 持久化服务每个普通命令先写 prepared，再写 committed；当前每次都会序列化完整记录，其中包含不断增长的命令历史。
3. 模型页已经默认两次调用，正常动作预算上限为 3 次（含一次修复）；库层标准模式仍是四次。把四次改为两次已经实现，不能再计入本轮预期收益。
4. `tavernCharacterAgentV2UserPrompt` 使用缩进 JSON，另加引用索引；Chat Completions 请求又会附上完整 schema，并保留最多 40 条历史消息。消息条数上限不等于字节或 token 上限。

## 建议实施顺序

### 1. 先做本地快速模式：收益明确、改动最小

增加“正常 / 快速”推进选项，将快速模式的展示等待从 2,100 ms 改为 **200 ms**。让 `createNpcActivityLoop` 在调度下一回合时读取当前速度，而不是创建时固定延迟；保持同一时刻只运行一个人物回合，停止操作仍等当前提交结束。

以本次中位耗时估算，连续推进从 `163.78 + 2100 = 2263.78 ms` 降为 `163.78 + 200 = 363.78 ms`，约 **6.2 倍**。这是提出方案时的固定负载估算，没有计入浏览器开销；不能把它解释为真实模型快了 6.2 倍。快速模式现已实现，实际浏览器测量与验证见 [快速模式交付记录](./33_npc_activity_fast_mode.md)。

快速模式只改变墙钟时间下的展示节奏，保持模拟世界秒数、人物行为、回合次序和存档频率。渲染可按 200–250 ms 合并更新，但每条世界事件和人物回执仍保留。世界无待执行事项时，应显示安静状态并按下一次真实唤醒调度，避免持续提交空回合。

验收：相同输入在两档速度下产生相同世界事件；快速停止后不多跑下一回合；快速保存/读取不丢历史；用浏览器测量完成 100 个回合的总耗时和操作响应。

### 2. 再缩短真实模型的输入与输出

保留“候选生成 → 本地数学评价 → 人物自主选择并提交”两次调用因果链。优先尝试：

- 把输入中的缩进 JSON 改为紧凑 JSON；保留引用校验需要的 ID 和字段。单独记录序列化前后字节/token 变化。
- 分离稳定的角色基础资料与动态的本轮投影，避免在历史消息里重复积累完整规则和 schema；在供应商支持的范围内验证前缀复用，不能只根据代码排布宣称已经命中缓存。
- 给短理由、描述和候选条目设置合适的输出长度要求，删去重复复述。保留必要心理工具与事实引用；不要通过截断必需字段来缩短响应。
- 对 Chat Completions 的 40 条 transcript 增加总体 token/字节预算。先保留最近的有效交流与权威人物状态；长期记忆只在既有规则允许的时机整理，不能每回合增加一次摘要请求。
- 分别记录两次调用的排队/首 token、输入输出 tokens、缓存统计、完整响应时间、修复次数和最终提交时间。没有真实 provider 数据前不承诺百分比收益。

第一步质量门槛是现有 529 项契约持续通过；再对固定的一组上下文做原版/紧凑版盲评，重点检查人物动机、关系记忆、台词自然度与越权率。只有输出更短且行为质量可接受的方案才进入默认配置。

### 3. 优化持久化，减少每回合全量复制

基线中存储耗时与完整代际文件体积值得优化。建议把命令去重/租约与世界 checkpoint 分开保存：prepared 只写小型命令记录；成功后以一个事务提交新 checkpoint、命令结果和 revision。历史命令按 ID 独立读取，避免每个回合复制整个 commands 数组。命名存档继续保留不可变完整快照。

可以先复用本轮引入的 SQLite 作为事务存储，提供旧 JSON 记录的按需迁移；保留 repository 接口，避免把数据库细节扩散进人物决策代码。缓存不变的 definition，并以 revision 校验；回合常驻内存只作为后续优化，不能跳过跨进程冲突检测。

以这组负载为首轮工程目标：存储累计耗时 p50 从约 119 ms 降至 **60 ms 以下**，回合 p50 降至 **120 ms 以下**。这些是验收目标，并非已获得收益。必须保留每次已确认回合的持久性、崩溃恢复、重复命令幂等与跨模式隔离。

### 4. 最后考虑本地批量推进与有限并行

增加本地“推进 5 / 20 回合”接口，每个批次内部仍顺序结算、逐回合落盘；返回可续传的批次进度，中途失败保留已完成回合。这样可减少 HTTP 往返和频繁重绘，但不会消除模型调用延迟。真实模型的逐次授权与请求预算保持现行规则。

只并行准备互不依赖人物的局部投影、检索和候选材料。对话的后一句、共享物件的交付、同一人物的私有状态更新必须遵守依赖次序；最终世界提交串行，并在 revision 变化后重新验证。多人物同时调用模型应放在测量之后，避免用更多排队、费用和冲突换取表面的并行。
